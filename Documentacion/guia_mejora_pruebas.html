2. Primero: corregir los defectos confirmados

Los siguientes comportamientos se reprodujeron en el diagnóstico previo con objetos en memoria y mocks, sin acceder a la base. Sus salidas no son resultados de nuevos tests JUnit: debemos convertirlos en pruebas de regresión.

D1 · Confirmado · Prioridad alta

Eliminar el segundo ítem puede borrar el primero

Dónde: DetallePedido.equals(), línea 111, y Pedido.quitarDetalle(), línea 110.

Causa: dos detalles nuevos tienen ID nulo. La comparación de sus identificadores devuelve igualdad y List.remove() elimina el primer elemento que considera igual, aunque se haya solicitado quitar el segundo.

Por qué escapó: ModelosTest.pedidoAgregaYQuitaDetallesRecalculandoTotal() solo elimina el primer elemento. Ese escenario pasa incluso con el defecto.

  1. Reproducir en JUnit: agregar dos detalles sin ID, quitar el segundo y verificar la identidad del restante y el total.
  2. Corregir la identidad: la misma referencia debe ser igual a sí misma; dos instancias distintas sin ID no deben ser iguales; con IDs no nulos, comparar la identidad persistida.
  3. Revisar hashCode(): debe ser coherente con equals(). Considerar que el ID cambia al persistir; no cambiar el hash de un objeto mientras sea clave de un mapa o miembro de un conjunto hash.
  4. Ampliar los casos: eliminar primero, segundo y un detalle ajeno; comparar IDs iguales, diferentes y nulos. Revisar otros modelos con el mismo patrón sin cambiarlos a ciegas.

Aceptación: queda exactamente el detalle de $200, su referencia se conserva y el total es $200. El test debe fallar antes del arreglo y pasar después.

Prueba propuesta para agregar a ModelosTest

Ejemplo pendiente de incorporar y ejecutar. Usa los imports de JUnit y BigDecimal ya presentes en esa clase.

@Test
void quitarSegundoDetalleSinIdConservaElPrimero() {
    // Arrange: objetos distintos, todavía sin ID de base de datos.
    Pedido pedido = new Pedido();
    DetallePedido primero = new DetallePedido();
    primero.setPrecioUnitario(new BigDecimal("200.00"));
    DetallePedido segundo = new DetallePedido();
    segundo.setPrecioUnitario(new BigDecimal("50.00"));
    pedido.agregarDetalle(primero);
    pedido.agregarDetalle(segundo);

    // Act
    pedido.quitarDetalle(segundo);

    // Assert: comprobar identidad, no el mismo equals defectuoso.
    assertEquals(1, pedido.getDetalles().size());
    assertSame(primero, pedido.getDetalles().get(0));
    assertEquals(0, new BigDecimal("200.00")
            .compareTo(pedido.getTotal()));
}
D2 · Confirmado · Prioridad alta

Se libera una mesa aunque falle el cierre de un pedido

Dónde: MesaService.liberar(), líneas 77–83.

Causa: el servicio llama a ModificarEstado(), ignora su resultado y continúa marcando la mesa como libre. Puede informar éxito aunque un pedido siga activo.

Por qué escapó: el test verifica que se llamó al DAO, pero no simula ni comprueba un fallo de cierre. Tampoco basta con verificar llamadas para demostrar que hubo persistencia correcta.

  1. Crear una regresión: simular un error de cierre y exigir que no se llame a cambiarEstado(..., LIBRE).
  2. Corrección mínima: comprobar el resultado del cierre y propagar el error. Ajustar también el test exitoso para que sus mocks devuelvan respuestas de éxito explícitas.
  3. Corrección completa: cerrar todos los pedidos activos y liberar la mesa dentro de una misma transacción. Si falla el segundo cierre, también debe revertirse el primero.
  4. Integración: provocar un fallo intermedio y consultar desde otra conexión que todos los estados permanecen como antes.

Aceptación: ante un fallo, la mesa sigue ocupada, ningún cierre parcial queda confirmado y el usuario recibe un error. En éxito, se cierran solo pedidos activos y la mesa queda libre por la acción manual.

Prueba propuesta para agregar a MesaServiceTest

Usa los mocks, el servicio y los helpers mesa() y pedido() existentes. El mensaje es el contrato mínimo propuesto; la reversión completa necesita además una integración.

@Test
void noLiberaMesaSiFallaCerrarPedido() {
    when(mesaDAO.getMesaPorId(1))
            .thenReturn(mesa(1, 1, EstadoMesa.OCUPADA));
    when(pedidoDAO.getPedidosPorMesa(1))
            .thenReturn(List.of(pedido(10, EstadoPedido.ABIERTO)));
    when(pedidoDAO.ModificarEstado(10, EstadoPedido.CERRADO))
            .thenReturn("Error al modificar estado");

    String resultado = service.liberar(1);

    assertAll(
        () -> assertEquals("Error al modificar estado", resultado),
        () -> verify(mesaDAO, never())
                .cambiarEstado(1, EstadoMesa.LIBRE)
    );
}

3. Después: probar los fallos de persistencia

R1 · Riesgo identificado en código · Pendiente de reproducción en base

Detalle, total y stock pueden quedar desincronizados

En PedidoService.agregarItem(), líneas 143–159, se inserta el detalle, luego se actualiza el total y finalmente se descuenta stock. Las operaciones DAO usan conexiones propias. Devolver un error en el segundo o tercer paso no deshace lo ya guardado.

La corrección anterior agregó el descuento de stock que faltaba, pero no hizo atómica toda la operación. También deben revisarse crearPedido() y cancelarPedido(): ignoran algunos resultados de actualización del inventario.

Casos de fallo a incorporar; resultados esperados, no resultados ya obtenidos.
Fallo provocadoQué debe comprobar la prueba
No se inserta el detalleNo se cambia el total ni el stock. Conservar el test existente y verificar el estado persistido.
Falla la actualización del totalNo queda el detalle recién insertado; total y stock conservan sus valores anteriores.
Falla el descuento de stockSe revierten detalle y total; se informa error sin éxito parcial.
Falla una devolución al cancelarNo queda un pedido cancelado con devolución parcial del inventario.
Dos solicitudes compiten por el último stockNo se vende más de lo disponible ni queda stock negativo. Caso adicional de concurrencia, aún no reproducido.

Diseño propuesto: definir un límite transaccional por operación de negocio. La capa de persistencia debe reutilizar una única conexión para las escrituras relacionadas, confirmar al final y revertir ante cualquier error. No alcanza con envolver el servicio si los DAO siguen abriendo conexiones independientes. Evitar interpretar mensajes con contains("correctamente"): usar un resultado explícito o una excepción y traducirlo a texto en el límite con la interfaz.

Una transacción agrupa operaciones en la misma sesión y permite confirmarlas o revertirlas juntas; no revierte cambios ya confirmados fuera de ella. Referencia de COMMIT y ROLLBACK.

Cómo demostrarlo: cargar una fixture conocida en restomanager_test, provocar determinísticamente el fallo de una escritura y comparar detalle, total, stock y estados antes y después desde otra conexión. Los mocks sirven para validar la reacción del servicio, pero no prueban un rollback real. Para concurrencia, comprobar además la actualización condicional de stock o el bloqueo de filas que se decida implementar.

Si se exige 100 % literal: definir primero si se habla de líneas o ramas y sobre qué alcance. Después revisar cada marca roja y amarilla de JaCoCo. Estos cambios no garantizan por sí solos 100 %. 5. Cómo trabajar y registrar la evidencia

  1. Elegir un caso. Anotar requisito, entradas, resultado esperado y archivos afectados. Empezar por D1, luego D2 y R1.
  2. Agregar el test antes del arreglo. Ejecutarlo y conservar el fallo. Confirmar que falla por el defecto, no por imports, mocks incompletos o falta de base.
  3. Aplicar la corrección mínima. No cambiar una expectativa correcta para acomodarla al comportamiento incorrecto.
  4. Repetir el caso. Guardar el log exitoso y revisar los efectos secundarios, no solo el mensaje devuelto.
  5. Ejecutar ambas suites. Primero unitarias sin base; después integración sobre una base local desechable preparada con los scripts del proyecto.
  6. Regenerar cobertura y actualizar el informe. Comparar mediciones equivalentes y conservar evidencia fuera de target antes del próximo clean.

6. Cuándo considerar resuelto el trabajo

  1. D1 tiene una regresión que demuestra la eliminación correcta y protege el contrato de identidad.
  2. D2 no permite liberar una mesa tras un cierre fallido; una integración demuestra la reversión de cambios parciales.
  3. Detalle, total, stock y estado se mantienen consistentes ante fallos de persistencia en los flujos intervenidos.
  4. La matriz de estados y los reportes se verifican con resultados explícitos y datos conocidos.
  5. Todas las unitarias pasan sin base y las integraciones pasan sobre restomanager_test; no hay omisiones ocultas.
  6. JaCoCo está actualizado y cada brecha restante está identificada; si se acordó 100 %, se verifica ese contador sobre el alcance declarado.
  7. El informe conserva los fallos iniciales, las correcciones y los resultados finales. No se presenta una propuesta como si ya estuviera implementada.

Conclusión: el problema no es que el 22,5 % de los tests haya fallado. Falta cobertura y hay escenarios incorrectos que los tests existentes no distinguían. La solución es mejorar primero las pruebas y la consistencia del sistema, y luego medir cuánto código sigue sin verificar.
